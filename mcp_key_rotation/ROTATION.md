# Fleet Secret Rotation Runbook

Operational procedures for rotating every Secret in `fleet_secrets/secrets.fleet.yaml`.
The manifest is generated by `fleet_secrets/fleet_secrets.py` from `fleet_secrets/registry.yaml`
plus each chart's values files; every Secret in it is operator-owned (the charts never
create them), and the generator stamps each data key with its rotation class
(`fleet_secrets/fleet_secrets.py:296-305`).

Ground rules that apply to every procedure below:

- `secrets.fleet.yaml` holds live key material: mode 0600, gitignored, never committed
  (manifest header; the generator re-applies 0600 on every write, `fleet_secrets.py:493-494`).
- The generator's DEFAULT run rotates the API-key tier and nothing else (four-step
  routine below). Only keys in the selected tier are re-minted; `--keep` rotates nothing
  and just refreshes the file in place; the protected master key requires
  `--rotate-master-keys --yes` (`fleet_secrets.py:419-432`, tier gate `:468-485`,
  tier-only re-mint `:334-335`).
- `mcp-fleet-apikeys` is one logical key carried in FIVE namespaces: applygate-mcp,
  logsearch-mcp, mm-rag, searxng-mcp, workbench-mcp. The generator keeps every copy
  identical when minting (`fleet_secrets.py:338-341`). When rotating it by hand, change
  all five namespaces in the same change.
- Values marked `<FILL:...>` are external credentials (URLs, S3 keys, Fabric app
  registration, database URL). They are never minted (`fleet_secrets.py:40-45`, `177-188`);
  "rotating" them means rotating the credential in the system it belongs to and pasting
  the new value into the Secret so the two stay in sync.
- Kubernetes env-injected secrets are a boot-time snapshot: the kubelet reads the Secret
  once at container start and a running process's `os.environ` never changes. Per-request
  env re-reads alone therefore cannot deliver a rotation
  (`SQLhandler/src/sqlhandler/server.py:4331-4332`,
  `mcp_servers/K8S-MCP/src/k8s_mcp/server.py:2885-2897`). The exceptions are the two
  file-backed tiers: the five wired MCP charts (section 1) and mm-rag's model-keys mount
  - there, kubelet refreshes a mounted FILE in place and the app re-reads it live.
  Everything else in this document is restart-class.

## Routine rotation - the four steps

The generator has one entry point per tier. The DEFAULT run rotates the API-key tier
only - the per-app keys clients present to `/mcp` and `/v1` (`is_api_key`,
`fleet_secrets/fleet_secrets.py:244-246`): all five `mcp-fleet-apikeys` copies,
`k8s-mcp-2-0-apikey`, `sqlhandler-apikey`, and `RAG_API_KEY`. Nothing else moves unless
asked: `MEDIA_TOKEN_SECRET`, the model keys, and the external credentials (S3, Fabric,
Iceberg, database URL) are never in any tier, and `ezapp-deploy` is excluded from every
tier (`NOT_OWNED`, `:240-241`).

| command | rotates |
|---|---|
| `python3 fleet_secrets/fleet_secrets.py` | API keys only (the tier above) |
| `--gateway-admin` | + `pcai-llm-gateway-admin`/`admin-api-keys` |
| `--postgres` | + `pcai-llm-gateway-pg-auth`/`password` - class `coordinated`: the run prints the ALTER USER warning and the file stamps the key `coordinated` (`:344-349`, `:236`) |
| `--all` | gateway-admin + postgres |
| `--keep` | nothing - refresh the file in place |
| `--rotate-master-keys --yes` | the master key (refuses without `--yes`; re-entry cost, section 4.2) |

The routine:

1. Run the default command. It rewrites `secrets.fleet.yaml` (0600) and prints a
   "Rotated N key(s)" list to stderr - check it matches your intent (`:498-503`).
2. Add `--gateway-admin` / `--postgres` only if you need those tiers (`--postgres`
   commits you to the ordered procedure in section 5 - database first).
3. `kubectl apply -f fleet_secrets/secrets.fleet.yaml`.
4. Restart only the consumers that need it: the four file-backed MCP charts are HOT (no
   restart, section 1.1); `k8s-mcp`, `sqlhandler`, and the `mm-rag` deployment need a
   rollout restart; the gateway picks up its by-ref keys only on restart (section 4.1).

Zero-downtime note: the generated file carries only the NEW key; to overlap, temporarily
set the key to `<new>,<old>` before applying (every consumer that supports lists splits
on commas), move clients, then re-apply the generated file to drop the old key.

### What the default run rotates, per app

The file carries 16 Secrets; the default run re-mints 8 keys. Everything else is
carried unchanged so the apply stays a no-op for it.

| App | Rotated by the DEFAULT run | Carried unchanged (needs a flag or never) |
|---|---|---|
| MCP servers | `mcp-fleet-apikeys/api-keys` (applygate-mcp, logsearch-mcp, searxng-mcp, workbench-mcp) + `k8s-mcp-2-0-apikey/api-key` | - |
| RAG (`mm-rag`) | `mcp-fleet-apikeys/api-keys`, `rag-platform-keys/RAG_API_KEY` | `MEDIA_TOKEN_SECRET` (invalidates signed media URLs), `rag-model-keys/*` (provider keys + S3, external) |
| SQL (`sqlhandler`) | `sqlhandler-apikey/api-keys` | `fabric-credentials/*`, `iceberg-credentials/*` (must match the external systems) |
| PCAI LLM Gateway (`pcai-llm`) | **nothing** | `admin-api-keys` (`--gateway-admin`), `password` (`--postgres`), `master-key` (`--rotate-master-keys --yes`), `database-url` (external) |

So a bare `python3 fleet_secrets/fleet_secrets.py` never touches the gateway or
Postgres. `ezapp-deploy` is not in this file at all - that deployment belongs to
another owner, and a Secret present here would be written by `kubectl apply` even
when excluded from rotation.

Hot means: no pod restart - an ADDED and a REMOVED key both take effect on the next
request once kubelet syncs the mounted file. Two mechanisms exist: the MCP key file
re-read per request by the five wired charts (section 1), and the mm-rag model-keys
mount plus its 15 s watcher. Latency is kubelet Secret-volume sync, nominally up to
~60 s. Restart means: update the Secret, then a rollout restart; the new value is only
live in replaced pods.

## 1. MCP servers (applygate-mcp, k8s-mcp, logsearch-mcp, searxng-mcp, workbench-mcp)

> **Before relying on the hot tier:** the no-restart behaviour is a property of the
> CHART you have deployed, not of the Secret. A cluster still running the older
> charts is env-only for every server here, and rotating its keys needs a rollout
> restart. Deploy the charts that carry the `mcp-keys` volume + `<ENV>_FILE` env
> once (that rollout changes no key values - the `secretKeyRef` env is untouched),
> and every rotation after that is live for the four file-backed servers.

Every MCP server authenticates `/mcp` with API keys resolved through the fleet module
`pcai_utils/mcp_auth.py` (hardlinked into each server). Two tiers carry the SAME Secret:
a boot-time env var (comma-separated - the bootstrap/fallback) and, in the five wired
charts, the same Secret mounted read-only at `/etc/mcp-keys`. `configured_keys` resolves
each env name `X` to ONE source, never a union of the two: the file named by `X_FILE`,
when it is set and reads with at least one key, is THE LIVE SOURCE OF TRUTH - an added
key is accepted and a REMOVED key stops working on the next request, no restart
(`pcai_utils/mcp_auth.py:164-196`; precedence `:170-176`, decisive expression `:193`);
otherwise the env value applies. The env is excluded while the file reads because
`os.environ` is a boot-time snapshot - unioning it would make every rotated-away key
un-revocable (`:178-182`). Files are cached on `(st_mtime_ns, st_size)`: one stat, no
read, until the file moves (`:131-161`); keys split on commas AND newlines (`:99-108`);
a gone or empty file falls back to env, a corrupt/unreadable one keeps the last good
keys and logs once, and only a file that never read anything leaves the pod on the env
fallback (`:111-128`, `:143-146`). Fingerprint of the matched key: `sha256:<12hex>` (`:435`).

Union remains only ACROSS env names: a key present solely in the universal
`MCP_API_KEYS` env would not be revocable by the per-server file. These charts wire
only the per-server alias, so this is not live today - but if `MCP_API_KEYS` is ever
wired from a Secret, it needs its own `MCP_API_KEYS_FILE` mount (`:182`).

- applygate-mcp: `APPLYGATE_API_KEYS` + `APPLYGATE_API_KEYS_FILE=/etc/mcp-keys/api-keys`
  (`mcp_servers/applygate_mcp/helm/templates/deployment.yaml:111-125`, mount `:199-201`,
  volume `:215-218`; values `mcp_servers/applygate_mcp/helm/local/values.g2.yaml:190-192`)
- workbench-mcp: `WORKBENCH_API_KEYS` + `WORKBENCH_API_KEYS_FILE`
  (`mcp_servers/workbench_mcp/helm/templates/deployment.yaml:137-151`, mount `:248-250`,
  volume `:279-282`; values `mcp_servers/workbench_mcp/helm/local/values.g2.yaml:214-216`)
- logsearch-mcp: `LOGSEARCH_API_KEYS` + `LOGSEARCH_API_KEYS_FILE`
  (`mcp_servers/logsearch_mcp/helm/templates/deployment.yaml:75-89`, mount `:180-182`,
  volume `:186-189`; values `mcp_servers/logsearch_mcp/helm/local/values.g2.yaml:51-53`)
- searxng-mcp: `SEARXNG_API_KEYS` + `SEARXNG_API_KEYS_FILE`
  (`mcp_servers/searxng_mcp/helm/templates/deployment.yaml:187-201`, mount `:178-180`,
  volume `:89-92`; values `mcp_servers/searxng_mcp/helm/local/values.g2.yaml:201-203`)
- prometheus-mcp is wired the same way in its chart (`PROMETHEUS_API_KEYS_FILE`,
  `mcp_servers/prometheus_mcp/helm/templates/deployment.yaml:52-53`) but its site values
  set no key Secret, so it contributes no row to `secrets.fleet.yaml`.
- k8s-mcp: `K8S_MCP_API_KEY` <- `k8s-mcp-2-0-apikey`/`api-key`
  (`mcp_servers/K8S-MCP/helm/templates/deployment.yaml:42-49`; values
  `mcp_servers/K8S-MCP/helm/local/values.g2.yaml:64-65`)
- ezapp-deploy: NOT in this file (another owner's deployment). Its `EZAPP_MCP_API_KEY`
  is wired from its own Secret; nothing here touches it.

### 1.1 Rotate mcp-fleet-apikeys (one distinct key per namespace) - HOT, no restart

Mint the replacement: `openssl rand -hex 32`.

1. Put the overlap value into all five Secrets - new key first, old key second, one
   Secret per namespace, identical values (the generator minted the five copies
   identically, `fleet_secrets.py:338-341`):

   ```bash
   for NS in applygate-mcp logsearch-mcp searxng-mcp workbench-mcp; do
     kubectl -n "$NS" patch secret mcp-fleet-apikeys --type merge -p \
       '{"stringData":{"api-keys":"NEW_KEY,OLD_KEY"}}'
   done
   kubectl -n mm-rag patch secret mcp-fleet-apikeys --type merge -p \
     '{"stringData":{"api-keys":"NEW_KEY,OLD_KEY"}}'   # restart-class there - see 2.3
   ```

2. Wait for kubelet to sync the mounted file (nominally up to ~60 s), then verify the
   file actually refreshed - NO rollout restart anywhere:

   ```bash
   kubectl -n applygate-mcp exec deploy/<name> -- cat /etc/mcp-keys/api-keys
   kubectl -n applygate-mcp exec deploy/<name> -- ls -l /etc/mcp-keys/api-keys
   ```

   `cat` must show the two-entry list (comma- and newline-separated keys both parse,
   `pcai_utils/mcp_auth.py:99-108`) and the mtime proves the kubelet synced it. Then one
   authenticated call with the NEW key succeeds (Bearer or `X-API-Key`, `:212-227`) -
   accepted by the per-request file-first resolution with no restart (`:164-196`).

3. Migrate clients to the new key. The old key keeps authenticating throughout: the
   overlap list still carries it in the file.

4. Retire the old key - also HOT: patch each Secret to the new value alone. Once
   kubelet syncs the file, the file is the only consulted source and the env snapshot is
   not: the retired key is refused on the next request with NO restart
   (`pcai_utils/mcp_auth.py:170-176`, `:193`). One operational caveat: if the mounted
   file ever goes missing or empty, the env fallback resurrects the boot snapshot
   (`:143-146`) - keep the Secret well-formed and re-verify after any volume hiccup.

**Option A - overlap rotation (above).** Both keys authenticate during the migration
window; accepting AND retiring keys are hot - no restart at any step.

**Option B - hard cut.** Patch the single new value: the old key is refused on the next
request after kubelet syncs the file (~60 s residual window); no restart, and the env
snapshot is not consulted while the file reads. Use only when you control every client.

The generator's DEFAULT run is the routine path for this key: the API-key tier re-mints
all five copies in one run - each namespace gets its OWN distinct value - plus
`k8s-mcp-2-0-apikey`, `sqlhandler-apikey` and `RAG_API_KEY` in the same run
(`:244-246`). Apply, then: nothing to restart for the four file-backed charts; rollout
restart for `k8s-mcp`, `sqlhandler` and the `mm-rag` deployment (sections 1.2, 2.3,
3.1). The four hot copies are class `hot` in the generated file (`:61-78`).

### 1.2 Rotate k8s-mcp-2-0-apikey (single-value key)

`ezapp-deploy` is OUT OF SCOPE: it belongs to another owner, its Secret is not in
`secrets.fleet.yaml`, and nothing in this runbook rotates or writes it. If that
deployment's key needs rotating, its owner does it.

`K8S_MCP_API_KEY` does NOT parse a comma list - it is compared as one shared value
(`mcp_servers/K8S-MCP/src/k8s_mcp/server.py:2889-2892`; the comma-list union comes from
`MCP_API_KEYS`, which the k8s-mcp chart does not wire). Its chart was NOT wired for the
file tier (no `mcp-keys` volume, no `*_FILE` env): K8S-MCP resolves keys with its own
env-only `_shared_keys()` (`mcp_servers/K8S-MCP/src/k8s_mcp/server.py:2885-2897`), so it
stays restart-class. Overlap rotation is not available - the procedure is a hard cut:

1. Hand every client the new key first (out-of-band).
2. Patch and roll:

   ```bash
   kubectl -n k8s-mcp patch secret k8s-mcp-2-0-apikey --type merge -p '{"stringData":{"api-key":"NEW_KEY"}}'
   kubectl -n k8s-mcp rollout restart deployment
   ```

   Check afterwards: rollout status; authenticated call with the new key; old-key calls
   now 401. k8s-mcp execs into pods and is write-capable - treat the window between
   step 1 and step 2 as the only safe time to invalidate the old key.

### 1.3 Rotate searxng-se-g2-secret

`SEARXNG_SECRET` is env-injected from `searxng-se-g2-secret`/`secret`
(`mcp_servers/searxng_mcp/helm/templates/deployment.yaml:103-114`; values
`mcp_servers/searxng_mcp/helm/local/values.g2.yaml:60-61`). It stays restart-class: it
is not an API-key list, and the chart wires it env-only with no file tier. Searxng is
stateless search;
the secret covers its internal session/state signing, so rotation costs only in-memory
state:

1. `kubectl -n searxng-mcp patch secret searxng-se-g2-secret --type merge -p '{"stringData":{"secret":"NEW_VALUE"}}'`
2. `kubectl -n searxng-mcp rollout restart deployment`
3. Check afterwards: rollout status; a search request through the service returns results;
   in-flight browser sessions reset (expected).

## 2. RAG (mm-rag namespace)

Three Secrets, three different behaviors.

### 2.1 rag-model-keys - hot rotation, no restart

The user-owned model Secret (`modelSecrets.existingSecret: rag-model-keys`,
`MultimodalRAG/helm-scale-large/local/values.g2.yaml:189`) is BOTH envFrom'd at boot AND
mounted as a volume at `/etc/rag/model-keys-user` on every consuming container
(`MultimodalRAG/helm-scale-large/templates/deployment.yaml:108-121` envFrom,
`:152-156` `CONFIG_DIR`, `:294-295` mount; the MCP container repeats the pattern at
`:404-408`; the embed-batcher at `MultimodalRAG/helm-scale-large/templates/embed-batcher.yaml:60-61`,`:80-81`).
The hot path is the mount: a watcher thread polls the `CONFIG_DIR` directories every 15 s
(default `CONFIG_RELOAD_INTERVAL`, `MultimodalRAG/src/multimodal_rag/model_config.py:268-282`),
re-applies every file into `os.environ` (`apply_config_dirs`, `model_config.py:238-252`),
and rebuilds the model objects; a failed rebuild keeps the previous configuration and
keeps polling (`model_config.py:299-300`). The watcher is wired in the API server
(`api_server.py:2034-2037`), the MCP server (`mcp_server.py:1544-1551`), and the embed
batcher (`embed_batcher.py:50-53`).

1. Patch the key you are rotating (the upstream provider must already accept the new
   value - these are upstream API keys and endpoints, not self-minted):

   ```bash
   kubectl -n mm-rag patch secret rag-model-keys --type merge -p \
     '{"stringData":{"MODEL_EMBEDDER_API_KEY":"NEW_UPSTREAM_KEY"}}'
   ```

2. Wait out kubelet sync (up to ~60 s) plus one 15 s poll.
3. Check afterwards:

   ```bash
   kubectl -n mm-rag logs deploy/<api-deployment> | grep 'Hot-reloaded model configuration'
   ```

   That line is emitted by the watcher on success (`model_config.py:298`). Confirm the API
   `/v1/models` probe or one real embed/query call succeeds with the new key. If the
   reload line does NOT appear, check the mount actually changed
   (`kubectl -n mm-rag exec <pod> -- ls -l /etc/rag/model-keys-user`); a failed reload logs
   "Config reload failed" and keeps the previous configuration (`model_config.py:300`).

No restart is needed for any consumer. The envFrom copy in already-running pods is stale
after this change, which is harmless: the watcher overwrites `os.environ` from the files
(`model_config.py:296`).

**Option A - targeted patch (above).** One key, one namespace, no restart.

**Option B - none.** The model keys are NOT in any generator tier (`is_api_key` only
matches `api-keys`/`api-key`/`RAG_API_KEY`, `fleet_secrets.py:244-246`): a default run
leaves `rag-model-keys` untouched, so direct patching (Option A) is the only path for a
single provider key.

### 2.2 rag-platform-keys - restart

`RAG_API_KEY` and `MEDIA_TOKEN_SECRET` are env-injected via `secretKeyRef` from
`security.existingSecret` (`rag-platform-keys`, values
`MultimodalRAG/helm-scale-large/local/values.g2.yaml:246-248`) into the REST container
(`deployment.yaml:164-176`) and the MCP container (`:412-421`); the watched-sources
CronJob reads both on every run (`templates/watched-sources-cronjob.yaml:270-279`).

1. Patch:

   ```bash
   kubectl -n mm-rag patch secret rag-platform-keys --type merge -p \
     '{"stringData":{"RAG_API_KEY":"NEW_KEY"}}'
   ```

2. `kubectl -n mm-rag rollout restart deployment` (both containers). CronJobs pick the new
   value up on their next run; no action needed there.

A default generator run re-mints `RAG_API_KEY` (it is in the API-key tier,
`fleet_secrets.py:244-246`) but NEVER `MEDIA_TOKEN_SECRET` (not in any tier) - either
way the rollout restart above is still required.
3. Check afterwards: authenticated REST call with the new `RAG_API_KEY`; MCP client
   reconnects.

**Do not rotate `MEDIA_TOKEN_SECRET` casually:** it is the HMAC key for signed
protected-media URLs - changing it invalidates every signed media URL issued before the
change (the chart itself fails an upgrade that would mint a new one, `templates/secret.yaml:139-142`).
Rotate it only on suspicion of compromise, and expect old shared links to break.

### 2.3 mcp-fleet-apikeys (mm-rag copy) - restart

Keep the VALUE in lockstep with the other four namespaces (one logical key,
`fleet_secrets.py:338-341`), but this copy is restart-class: the RAG MCP server resolves
keys through the same fleet `configured_keys` from env only - `MCP_API_KEYS` /
`RAG_API_KEYS` (`MultimodalRAG/src/multimodal_rag/mcp_server.py:56-59`, `:949`) - and its
chart sets no `*_FILE` env and mounts no key directory
(`MultimodalRAG/helm-scale-large/templates/deployment.yaml:423-431`).

1. Patch the mm-rag copy (same overlap value as section 1.1 step 1).
2. `kubectl -n mm-rag rollout restart deployment`; check `rollout status`.
3. Check afterwards: one authenticated MCP call with the new key succeeds.

## 3. SQLhandler (sqlhandler namespace)

Two independent key planes: the static `/mcp` keys (env, restart-class) and the
administration plane (policy file + minted-keys store, both hot-reloaded on mtime).

### 3.1 sqlhandler-apikey (static /mcp keys)

`MCP_API_KEYS` is wired unconditionally from `security.apiKey.existingSecret`
(`sqlhandler-apikey`/`api-keys`, `SQLhandler/helm/templates/deployment.yaml:156-160`; values
`SQLhandler/helm/local/values.g2.yaml:212-213`). Keys are comma-separated and every entry
authenticates; the env is re-read per request (`SQLhandler/src/sqlhandler/server.py:4329-4332`,
`:4364`) - which still requires a restart to take effect, per the ground rule above.

1. Overlap value:

   ```bash
   kubectl -n sqlhandler patch secret sqlhandler-apikey --type merge -p \
     '{"stringData":{"api-keys":"NEW_KEY,OLD_KEY"}}'
   kubectl -n sqlhandler rollout restart deployment
   ```

2. Check afterwards: rollout status; authenticated `/mcp` call with the new key; minted
   keys from the admin store keep working throughout (the gate authenticates the union of
   env keys and the store, `server.py:4335-4354`).
3. Drop the old value once clients migrated; roll again.

**Option A - overlap rotation (above).** Preferred; no client lockout.

**Option B - hard cut.** Single value + one restart. Only when every key-holder is
coordinated; anything presenting the old key 401s.

### 3.2 The admin plane - lockout prevention and recovery

Admin rights do NOT come from the API-key Secret. They come from the policy file's
top-level `admins` list (subjects and/or key fingerprints,
`SQLhandler/src/sqlhandler/policy.py:258-263`, validated at `:616-648`), consulted by
`is_admin` (`SQLhandler/src/sqlhandler/admin_keys.py:450-498`). The bootstrap fallback -
"the configured API key IS the administrator" - applies ONLY while no policy document is
enforcing (`admin_keys.py:457-462`, `:487`; `SQLHANDLER_BOOTSTRAP_ADMIN`, chart default on,
`SQLhandler/helm/templates/deployment.yaml:162-168`). Once the policy enforces, a rotated
static key that is not re-designated loses the admin plane, and an admins list that pins
the OLD key's fingerprint (`key:sha256:<12hex>`, `SQLhandler/src/sqlhandler/identity.py:212`,`:252`)
never matches the new key (different fingerprint).

**Mitigation (do this now, not during an incident): designate admins by SSO subject, not
by key fingerprint.**

```json
{
  "admins": ["subject:andrew-bydlon"]
}
```

A subject caller matches both the bare name and the `subject:<name>` prefixed spelling
(`admin_keys.py:476-484`), and `owner_key` resolves the stable owner scope from the subject
BEFORE falling back to the key fingerprint (`policy.py:203-213`). A subject survives every
key rotation; a fingerprint survives none.

**Second-best (if you must pin keys): overlap rotation.** Keep the old key in the
`api-keys` list (section 3.1 Option A) until the policy's `admins` entry has been rewritten
to the new fingerprint - the old fingerprint keeps authenticating during the window.

**Recovery when already locked out** (admins list pins a fingerprint whose key was
rotated; every admin call refuses):

1. Exec into a running sqlhandler pod and edit the live policy file on the read-write
   policy claim (g2 uses claim mode on the dedicated RWX claim `sqlhandler-policy-rw`,
   `SQLhandler/helm/local/values.g2.yaml:239-264`; env `SQLHANDLER_POLICY_FILE`,
   `SQLhandler/helm/templates/deployment.yaml:238-239`):

   ```bash
   POD=$(kubectl -n sqlhandler get pod -l app.kubernetes.io/name=sqlhandler -o jsonpath='{.items[0].metadata.name}')
   kubectl -n sqlhandler exec -it "$POD" -- vi /etc/sqlhandler-policy/policy.json
   # add or replace the admins entry, e.g. "admins": ["subject:andrew-bydlon"]
   ```

2. Save. Nothing else to do: the policy store hot-reloads on mtime
   (`policy.py:1222-1230`), the admins designation hot-reloads with the file
   (`policy.py:1153-1155`), and the load logs the new admin count (`policy.py:1274-1282`).
3. Check afterwards: `kubectl -n sqlhandler logs <pod> | grep 'admins='` shows the new
   count; an admin-plane call (policy editor or the MCP admin twins) succeeds.

In ConfigMap mode (no claim) the policy mount is READ-ONLY
(`SQLhandler/helm/templates/deployment.yaml:373-375`, `:488-490`): edit the ConfigMap
object instead (`kubectl -n sqlhandler edit configmap <policy-configmap>`); kubelet syncs
the mount and the same mtime reload applies it. On the g2 site with
`seedFromConfigMap: true` (`values.g2.yaml:264`) the ConfigMap is only a FIRST-BOOT seed -
after seeding the FILE is the truth and ConfigMap edits stop applying
(`values.g2.yaml:246-250`).

A broken edit never unmasks callers and keeps the previous policy
(`policy.py:1243-1246`); if no policy ever loaded, an invalid file fails CLOSED (all
covered tables hidden) until fixed (`policy.py:1247-1260`).

### 3.3 fabric-credentials and iceberg-credentials (external, restart)

These are external credentials: the values must MATCH the Fabric app registration / the
Iceberg catalog and object store - rotate them at the source system first, then paste.

1. Rotate in the source system (Fabric portal: new client secret; catalog/storage: new
   keys or token).
2. Patch the Secret - keys are `tenant-id`/`client-id`/`client-secret` wired to
   `FABRIC_TENANT_ID`/`FABRIC_CLIENT_ID`/`FABRIC_CLIENT_SECRET`
   (`SQLhandler/helm/templates/deployment.yaml:71-89`; key names from
   `values.g2.yaml:310-314`), and `token`/`access-key`/`secret-key` wired to
   `ICEBERG_CATALOG_TOKEN`/`S3_ACCESS_KEY`/`S3_SECRET_KEY` (`deployment.yaml:104-127`;
   key names `values.g2.yaml:354-358`):

   ```bash
   kubectl -n sqlhandler patch secret fabric-credentials --type merge \
     -p '{"stringData":{"client-secret":"NEW_SECRET"}}'
   kubectl -n sqlhandler rollout restart deployment
   ```

3. Check afterwards: rollout status; a query against the affected backend succeeds; check
   the pod logs for credential/auth errors on the first queries. There is no overlap
   option: the source system accepts one secret at a time, so restart promptly after the
   source-side rotation.

## 4. PCAI LLM Gateway (pcai-llm namespace)

### 4.1 pcai-llm-gateway-admin (admin-api-keys) - routine hygiene

Admin API keys for `/admin` are env-injected from `pcai-llm-gateway-admin`/`admin-api-keys`
(`PCAI_LLM/helm/templates/deployment.yaml:608-617`; values
`PCAI_LLM/helm/local/values.g2.yaml:57-58`). They are comma-separated and every entry
authenticates (`PCAI_LLM/src/pcai_llm/config.py:122`, split at
`PCAI_LLM/src/pcai_llm/api/routes_admin.py:99`); they are NEVER database rows, so rotating
them cannot corrupt state (`routes_admin.py:6`), and an EMPTY list disables the whole admin
API, fail-closed (`routes_admin.py:18`, `config.py:122`). The generator touches this
key only with `--gateway-admin` or `--all` (`fleet_secrets.py:482`); a default run
leaves it alone. The zero-downtime overlap note at the top of this runbook applies here.

**Option A - overlap rotation (preferred):**

1. ```bash
   kubectl -n pcai-llm patch secret pcai-llm-gateway-admin --type merge -p \
     '{"stringData":{"admin-api-keys":"NEW_KEY,OLD_KEY"}}'
   kubectl -n pcai-llm rollout restart deployment/pcai-llm-gateway
   ```
2. Check afterwards: rollout status; admin panel login with the NEW key.
3. Drop the old key (patch to just the new value) and roll again once every admin has the
   new key.

**Option B - immediate cut:** single new value + one restart. Old admin keys die at the
restart. Use when an admin key may be compromised - otherwise Option A.

### 4.2 pcai-llm-gateway-secrets (master-key) - DO NOT ROTATE BY DEFAULT

> **DESTRUCTIVE. Rotating this key invalidates EVERY stored endpoint credential, by
> design, with no recovery path.**

The master key is the single Fernet key, SHA-256-derived, no key ring
(`PCAI_LLM/src/pcai_llm/core/secretbox.py:8-11`): every upstream API key saved through the
admin panel is stored encrypted in Postgres under it, and a rotated master key must not
silently keep decrypting old material. After rotation the gateway does not crash - each
lookup degrades to unauthenticated and the UPSTREAM 401s visibly (`secretbox.py:13-15`) -
but every panel-stored credential is gone until re-saved.

The generator agrees: `master-key` is in `NEVER_KEYS` (`fleet_secrets.py:57-59`), the
renderer refuses to re-mint it (`fleet_secrets.py:323-333`), and the only override is
`--rotate-master-keys`, which without `--yes` prints the stop-warning and exits 2
(`fleet_secrets.py:356-371`, `:419-432`). Rotation classes stamped in
`secrets.fleet.yaml` mark it `never` (`fleet_secrets.py:61-78`).

**Routine hygiene: rotate `admin-api-keys` (section 4.1) instead.** There is no
operational reason to touch the master key.

**Only rotate on suspected compromise.** Procedure, accepting the re-entry cost:

1. Stop using the admin panel for credential edits.
2. Rotate with explicit confirmation:

   ```bash
   python3 fleet_secrets/fleet_secrets.py --rotate-master-keys --yes
   kubectl apply -f fleet_secrets/secrets.fleet.yaml
   kubectl -n pcai-llm rollout restart deployment/pcai-llm-gateway
   ```

   The command prints the re-entry warning (`fleet_secrets.py:356-371`) - read it before
   `--yes`. Check afterwards: `git diff`-free manual diff of `secrets.fleet.yaml` shows ONLY
   the `master-key` value changed; rollout status; the gateway serves `/health`.
3. Re-save EVERY endpoint credential that was saved as a PANEL value (`auth_token_enc` -
   Fernet ciphertext under the master key, `PCAI_LLM/src/pcai_llm/routing/router.py:58`).
   By-reference endpoints are NOT affected and need NO /admin re-registration: the
   database stores only the Secret NAME (`model_endpoints.api_key_secret`,
   `PCAI_LLM/src/pcai_llm/db/schema.py:489`; `PCAI_LLM/src/pcai_llm/routing/router.py:57`)
   and the chart injects the VALUE as env at pod start
   (`PCAI_LLM_UPSTREAM_KEY__<SUFFIX>` / `PCAI_LLM_MCP_KEY__<SUFFIX>`,
   `PCAI_LLM/helm/templates/deployment.yaml:576-595`) - so rotating the referenced
   Secret plus the gateway restart in step 2 is sufficient.
4. Check afterwards: for each endpoint, one real completion/request through the gateway
   succeeds; no upstream 401s in the gateway logs.

## 5. Postgres (pcai-llm namespace)

Two modes, two Secrets (`PCAI_LLM/helm/local/values.g2.yaml:79-89`):

- **Embedded** (`database.embedded.enabled: true`): the gateway reads the password from
  `pcai-llm-gateway-pg-auth`/`password` into `PCAI_LLM_DB_PASSWORD`
  (`PCAI_LLM/helm/templates/deployment.yaml:633-637`); the co-deployed Postgres
  StatefulSet reads the SAME Secret into `POSTGRES_PASSWORD` (`templates/postgres.yaml:78-82`).
- **External**: the gateway reads the full connection string from
  `pcai-llm-gateway-db`/`database-url` into `PCAI_LLM_DATABASE_URL`
  (`deployment.yaml:639-643`).

The generator makes this hard to do casually: `pcai-llm-gateway-pg-auth` is class
`coordinated` (`fleet_secrets.py:74-77`) - the generated file stamps it `must be
changed in the backing system FIRST` (`:236`) and a `--postgres` run that rotates it
prints the ALTER USER warning (`:344-349`).

The fact that dictates the order of operations: **`POSTGRES_PASSWORD` seeds the data
directory on FIRST initdb only.** The pg-auth Secret carries the chart annotation
`pcai-llm-gateway.io/pg-init-once: "true"` with exactly this warning
(`PCAI_LLM/helm/templates/secrets-managed.yaml:85-87`), and the Secret is
`helm.sh/resource-policy: keep` (`:60`, `:84`). Changing the Secret alone NEVER changes the
database's actual password; changing the database requires the Secret to follow before
any pod that reads it restarts.

> **ORDER IS LOAD-BEARING: database first, then Secret, then restart. Reversing it breaks
> authentication.** If you update the Secret first and a gateway pod (or the StatefulSet)
> restarts before the `ALTER USER`, every new connection presents the NEW password against
> a database that still has the OLD one - the gateway fails readiness/503s through
> fail-closed /ready, and if the ALTER is forgotten the outage is permanent. The database
> itself is unaffected either way (Postgres ignores `POSTGRES_PASSWORD` on an existing
> data dir) - the casualty is the gateway's ability to connect.

### 5.1 Embedded mode - in-place password rotation

1. Change the password IN the database first. Find the PG pod (StatefulSet/service
   `pcai-llm-gateway-pg`, label `app: pcai-llm-gateway-pg`,
   `templates/postgres.yaml:3`,`:18-19`,`:38`; default username/database from
   `database.embedded.auth.username`/`.database`):

   ```bash
   PGPOD=$(kubectl -n pcai-llm get pod -l app=pcai-llm-gateway-pg -o jsonpath='{.items[0].metadata.name}')
   kubectl -n pcai-llm exec -it "$PGPOD" -- env | grep POSTGRES_USER   # confirm the superuser name
   kubectl -n pcai-llm exec -it "$PGPOD" -- psql -U <username> -d <database> \
     -c "ALTER USER <username> WITH PASSWORD 'NEW_PASSWORD';"
   ```

   From this instant the OLD password is dead for NEW connections; live pooled
   connections keep serving (in-place rotation has an unavoidable brief window here -
   that is what Option B below removes).

2. Update the Secret to match IMMEDIATELY (minimize step-1-to-step-2 time):

   ```bash
   kubectl -n pcai-llm patch secret pcai-llm-gateway-pg-auth --type merge -p \
     '{"stringData":{"password":"NEW_PASSWORD"}}'
   ```

   Check afterwards: `kubectl -n pcai-llm get secret pcai-llm-gateway-pg-auth -o jsonpath='{.data.password}' | base64 -d`
   matches the value you set in step 1.

3. Restart ONLY the gateway - never the StatefulSet (nothing there needs to change, and a
   fresh data dir would re-seed from the Secret):

   ```bash
   kubectl -n pcai-llm rollout restart deployment/pcai-llm-gateway
   kubectl -n pcai-llm rollout status deployment/pcai-llm-gateway
   ```

4. Check afterwards: gateway `/ready` passes; one control-plane or ledger write succeeds
   (the gateway applies its schema at startup either way, `deployment.yaml:618-623`); no
   `password authentication failed` lines in gateway or PG logs.

**What breaks if the order is reversed:** Secret-then-DB means every pod replaced between
the Secret change and the ALTER authenticates with a password the database does not know -
CrashLoopBackOff / fail-closed 503s on the gateway; if the ALTER never happens, the
gateway is down for good while Postgres is perfectly healthy. DB-then-never-Secret is the
mirror image: the first future pod replacement re-breaks auth silently.

### 5.2 Embedded mode - Option B: two-role swap (zero-downtime)

Removes the new-connection window of the in-place ALTER by never reusing a role:

1. Create a sibling role in the database while the old one still serves:

   ```bash
   kubectl -n pcai-llm exec -it "$PGPOD" -- psql -U <username> -d <database> \
     -c "CREATE ROLE <gateway_next> LOGIN PASSWORD 'NEW_PASSWORD';" \
     -c "GRANT ALL PRIVILEGES ON DATABASE <database> TO <gateway_next>;" \
     -c "GRANT <old_role_name> TO <gateway_next>;"   # schema/ownership inheritance
   ```

   The old role is untouched: existing and new connections keep working throughout.

2. Point the gateway at the new role. The username is values-driven
   (`database.embedded.auth.username`, `deployment.yaml:629-630`), so this is a
   `helm upgrade` with the new username AND the pg-auth Secret already holding the new
   role's password - do the Secret patch and the upgrade in the same change. The pod
   template change rolls the gateway; the StatefulSet ignores the change
   (`POSTGRES_PASSWORD` is initdb-only, `secrets-managed.yaml:85-87`).
3. Check afterwards: rollout status; schema/ledger writes succeed under the new role;
   then revoke the old role once verified:

   ```bash
   kubectl -n pcai-llm exec -it "$PGPOD" -- psql -U <username_next> -d <database> \
     -c "REASSIGN OWNED BY <old_role_name> TO <gateway_next>;" \
     -c "DROP OWNED BY <old_role_name>;" \
     -c "DROP ROLE <old_role_name>;"
   ```

   Check afterwards: the dropped role no longer authenticates; the gateway is unaffected.

Trade-off: Option B has more steps and needs a values change, but every step is
rollback-safe (old role valid until explicitly dropped); Option A is two commands plus a
restart with a bounded window. For a planned rotation choose B when the gateway is
multi-replica and busy; A is fine for a quiet single-replica deployment.

### 5.3 External mode - pcai-llm-gateway-db

The upstream database is not owned by this chart; rotate there first.

1. In the external Postgres: create the new password (or a new role - same two-role
   pattern as 5.2 applies if the upstream supports it and you need zero downtime).
2. Write the new full URL into the Secret:

   ```bash
   kubectl -n pcai-llm patch secret pcai-llm-gateway-db --type merge -p \
     '{"stringData":{"database-url":"postgresql://<user>:<new-password>@<host>:<port>/<db>"}}'
   kubectl -n pcai-llm rollout restart deployment/pcai-llm-gateway
   kubectl -n pcai-llm rollout status deployment/pcai-llm-gateway
   ```

   The same order-of-operations rule applies: the URL in the Secret must be VALID at the
   upstream database before any gateway pod restarts, or the replaced pods cannot connect.
3. Check afterwards: rollout status; control-plane queries and the usage ledger both
   succeed; no connection-refused/auth errors in gateway logs. Rollback = re-patch the
   OLD URL and restart (keep the old upstream credential valid until verified).

## 6. Verification checklist

Run after every rotation in this document:

- [ ] `kubectl -n <ns> get secret <name> -o jsonpath='{.data.<key>}' | base64 -d` shows the
      intended new value (and ONLY the intended keys changed).
- [ ] No pod is in `CreateContainerConfigError` (a missing/renamed Secret - the charts
      fail loud by design on every env-wired key).
- [ ] `kubectl -n <ns> rollout status deployment/<name>` completes; no new
      restarts/OOMKills in `kubectl -n <ns> get pods`.
- [ ] One authenticated call per consumer with the NEW credential succeeds (Bearer or
      `X-API-Key`, whichever the client uses).
- [ ] **MCP hot tier (applygate/logsearch/searxng/workbench):** BOTH operations are
      hot - the new key is accepted AND a removed key is refused with NO restart:
      `kubectl -n <ns> exec deploy/<name> -- cat /etc/mcp-keys/api-keys` shows the new
      list and `ls -l` a fresh mtime (kubelet actually synced); while the file reads,
      the env snapshot is not consulted, so a retired key is refused on the next request
      (`pcai_utils/mcp_auth.py:170-176`, `:193`).
- [ ] During overlap windows only: the OLD credential still authenticates; after the
      final cut: it returns 401.
- [ ] Generator sanity (after any generator use): the stderr `Rotated N key(s)` list
      matches the tier you intended (`fleet_secrets.py:498-503`); confirm all five
      `mcp-fleet-apikeys` copies carry the identical value (`fleet_secrets.py:338-341`);
      confirm `master-key` was NOT touched; `--keep` refreshes the file without rotating
      anything (`:422`, `:472`).
- [ ] Secrets file still mode 0600 after any generator run (`fleet_secrets.py:493-494`).

Per-rotation extras:

- [ ] **rag-model-keys (hot):** "Hot-reloaded model configuration" in api, mcp and
      embed-batcher logs (`model_config.py:298`); no "Config reload failed" lines
      (`:300`); one real embed/query succeeds.
- [ ] **rag-platform-keys:** REST auth works with the new `RAG_API_KEY`; if
      `MEDIA_TOKEN_SECRET` was touched, accept that pre-change signed media URLs are dead
      (`templates/secret.yaml:139-142`).
- [ ] **sqlhandler-apikey:** minted keys from the admin store still authenticate
      (`server.py:4335-4354`); admin plane still reachable; if admins are pinned by

- [ ] **pcai-llm-gateway-admin:** admin panel login with the new key; a second admin key
